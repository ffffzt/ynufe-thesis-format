# 计算机科学与技术类毕业论文（设计）写作指导

**来源**：《计算机科学与技术类毕业论文（设计）写作指导》，云南财经大学中华职业学院智慧技术教学部，二〇二六年九月。面向毕业班学生与指导教师，讲的是「每一步怎么做、做成什么样算合格」。

**配套**：[zhonghua-cs-2023-spec.md](zhonghua-cs-2023-spec.md)（同部门同期印发的《规范要求》，含全部硬性格式数字与评分条款）。

本文件是便于执行的重述，不是原文照录。写作要求与指导教师意见冲突时，以指导教师为准。

## 1 计算机类毕业设计是什么

围绕特定软件系统开发、数据处理与分析、人工智能应用、网络系统设计、硬件嵌入式开发或计算机技术研究等课题，用软件工程方法完成**需求分析 → 系统设计 → 编码实现 → 测试验证 → 论文撰写**全过程的综合性实践成果。

核心特征：**以可运行的系统/模型/设计方案 + 规范的技术文档为核心成果**，侧重工程实践与技术实现。

与相邻类型的分界：

| 不是 | 因为 |
| --- | --- |
| 调查报告类 | 那以一手调查数据为证据；本类必须有可演示的作品 |
| 理论研究型 | 那侧重算法创新或理论证明；本类**不要求原创性理论创新** |
| 案例分析型 | 那以剖析已有案例为主；本类要求亲手从无到有做出完整系统 |

**总流程**：选题 → 需求分析与系统设计（开题）→ 开发环境搭建 → 编码实现 → 测试调试 → 论文撰写 → 查重与修改 → 答辩。每一环节都要留下过程材料（需求文档、设计文档、源代码、测试用例、版本记录），作为中期检查和答辩核查的依据。

## 2 选题

### 六条原则

贴合专业培养目标；工程实践导向（优先结合毕业实习、教师科研课题、学科竞赛项目）；难度与工作量适度（符合高职本科层次，经努力能完成）；理论与实践结合（避免纯代码堆砌）；鼓励创新但避免盲目追前沿；**一人一题**，团队项目须明确个人独立完成的模块。

### 六大题目类型与成果要求

与《规范要求》第 7 节同表，此处补上各类的知识点侧重：

| 类型 | 典型方向 | 成果要求要点 |
| --- | --- | --- |
| 软件开发类 | Web / 移动 / 桌面（C/S）/ 游戏（Unity、Cocos） | 需求分析、总体设计、数据库设计、编码实现、测试部署全过程；可运行源代码、安装包/部署包、数据库脚本、使用手册、测试报告、说明书 |
| 数据工程类 | 数据分析与可视化、大数据（Hadoop/Spark/Flink）、采集与爬虫 | 采集、清洗、存储、分析建模、可视化全过程；数据处理程序、分析报告、可视化成果；数据来源真实可靠，结论有实际参考价值 |
| 人工智能类 | 机器学习、深度学习（CNN/RNN/Transformer）、智能系统 | 问题定义、数据准备、模型选择与训练、评估、集成部署；训练好的模型、完整代码、实验对比结果；**突出模型原理理解、参数调优过程与实验结果分析，禁止只调现成 API** |
| 网络与系统类 | 网络工程设计、网络安全应用、运维与云原生 | 设计方案、配置文档、实现代码或配置脚本、测试报告；方案须有可实施性 |
| 硬件与嵌入式类 | 嵌入式系统、物联网应用、智能硬件 | 硬件选型或电路设计、软件编程、系统联调、功能测试全过程；硬件实物（或详细方案与仿真结果）、源代码、电路原理图或接线图、调试记录、功能演示视频 |
| 论文类（≤10%） | 技术研究综述、教学改革与教育技术 | 综述：观点明确、资料详实、**参考文献 ≥25 篇、外文 ≥5 篇**，须有自己的分析对比与见解；教改：明确研究方案、实施过程与实证数据 |

### 四步选题

1. **确定方向**：结合技术栈（前端/后端/移动/AI/硬件）、专业背景与实习经历，圈定技术领域。
2. **调研现有方案**：查文献与开源项目，找出可改进或适合自己实现的切入点。
3. **缩小为具体课题**：收窄为「基于××技术的××系统设计与实现」，明确**为谁解决什么问题、用什么技术、包含哪些核心功能**。
4. **可行性检验**：技术可行性（技术栈是否在能力范围内、周期内能否完成）、资源可行性（环境、硬件、数据集能否获取）、**工作量（核心功能模块是否达到 5 个以上）**。确认后请指导教师审核把关。

### 题目拟定

- **不超过 25 个字**，不使用标点符号。
- 不用不常见的英文缩写（Web、App、AI 这类通用缩写可用）。
- 体现**技术 + 应用场景 + 核心功能**，让人一看便知「用什么技术做了什么系统」。

题目示例：基于 Spring Boot+Vue 的校园二手交易平台设计与实现｜基于微信小程序的社区团购系统设计与实现｜基于 Python 的电商用户行为分析与可视化系统｜基于卷积神经网络的花卉识别系统设计与实现｜基于 STM32 的智能温室环境监测系统设计｜中小企业网络规划与安全方案设计——以××公司为例。

### 选题常见问题与对策

| 问题 | 对策 |
| --- | --- |
| 过大过难（如「基于深度学习的通用人工智能系统」） | 把大系统缩为「一个具体场景下的完整小系统」，功能聚焦、边界清晰 |
| 过简（如「静态个人网页制作」） | 先评估技术能力与开发周期，再定功能范围，确保核心功能可独立实现 |
| 缺乏实际场景，为技术而技术 | 优先选自己熟悉的技术栈，新技术作为加分项而非全部依赖 |
| 盲目追热点但基础薄弱，只停留在调 API | 同上；核心算法必须自己能解释 |
| 题目不规范（过长、模糊、未体现技术与功能） | 按「基于××技术的××系统设计与实现」规范拟题 |
| 论文类选题比例过高 | 多数学生应选做系统开发类课题 |

## 3 系统设计

### 题目类型对应的研究范式

| 题目类型 | 核心范式 | 重点内容 |
| --- | --- | --- |
| 软件开发类 | 软件工程生命周期 | 需求分析 → 架构设计 → 详细设计 → 编码 → 测试 |
| 数据工程类 | 数据处理全流程 | 数据采集 → 清洗 → 存储 → 分析建模 → 可视化 |
| 人工智能类 | 机器学习工程流程 | 问题定义 → 数据准备 → 模型训练 → 评估调优 → 部署 |
| 网络与系统类 | 方案设计与验证 | 需求分析 → 拓扑/架构设计 → 配置实现 → 测试验证 |
| 硬件与嵌入式类 | 软硬件协同开发 | 硬件选型/设计 → 软件编程 → 联调测试 |
| 论文综述类 | 文献研究法 | 文献检索 → 分类梳理 → 对比分析 → 总结展望 |

本科毕业设计以**工程实现**为主，不追求技术创新的突破性。

### 需求分析与目标细化

1. **明确用户角色**：系统有哪些用户类型（普通用户、管理员、商家…），每种用户的核心诉求。
2. **功能需求分解**：按「总功能 → 一级模块 → 二级功能点」树形分解（类似 WBS）。
3. **非功能需求**：性能、安全性、易用性、兼容性等要求。

以「校园二手交易平台」为例，一级模块可拆为：用户管理、商品管理、交易管理、消息通知、后台管理；二级功能点如「用户管理：注册登录、个人信息维护、实名认证、收货地址管理」。最底层功能点就是后续编码的任务单元。

### 技术选型与架构设计

- 优先选自己熟悉、文档完善、社区活跃的成熟技术栈。
- 前后端技术匹配，架构模式明确（B/S、C/S、移动端、小程序）。
- 数据库与业务场景匹配（关系型 MySQL/PostgreSQL vs 非关系型 MongoDB/Redis）。

常见技术栈：后端 Spring Boot / Django·Flask / Express；前端 Vue.js、React、Element UI·Ant Design；移动端 Android Studio、微信小程序、Flutter、uni-app；数据库 MySQL、Redis、MongoDB；人工智能 Scikit-learn、PyTorch、TensorFlow、Pandas、NumPy；大数据 Hadoop、Spark、Flink、Kafka；嵌入式 STM32（Keil）、Arduino、树莓派。

架构设计要明确架构模式（MVC、MVVM、三层、微服务等），画出总体架构图，说明各层/各模块之间的调用关系与数据流向。

### 开发方法与工具

建议**增量迭代**：先完成核心功能的最小可用版本，再逐步完善辅助功能。

- 版本控制：**Git（必须使用，保留开发提交记录）**
- 开发工具：IDEA / PyCharm / VS Code / Android Studio
- 接口测试：Postman、Apifox
- 数据库管理：Navicat、DBeaver
- 建模：Visio、Draw.io、ProcessOn（用例图、流程图、架构图、E-R 图）

### 系统设计的输出：开题报告

应包含七项：选题背景与意义；国内外研究现状；研究内容与目标（明确要实现哪些功能模块）；拟采用的技术路线与实施方案（功能需求分析、技术选型、系统架构、开发环境、实施步骤）；所依托的理论基础（如 MVC 模式、关系数据库理论、B/S 架构原理、神经网络原理）；进度安排（按 **14 周**规划每阶段任务）；参考文献（**不少于 20 篇**）。

**技术路线图**按「需求分析 → 系统设计 → 数据库设计 → 编码实现 → 测试 → 部署 → 论文写作」绘制，展示各阶段先后关系与主要产出物。

## 4 论文结构：正文七章

**结构设计的一般过程**：先做概要设计规划整体框架（与系统开发实际过程对应，避免偏离主题或重复）→ 按「绪论 → 技术基础 → 分析 → 设计 → 实现 → 测试 → 总结」的软件工程逻辑划分章节 → 写作中定期做逻辑检查 → 按导师反馈调整 → 最终确认各部分有对应的设计图、代码、截图、测试结果支撑。

| 部分 | 主要内容 | 作用 |
| --- | --- | --- |
| 封面 | 题目、学生信息、指导教师、日期 | 标准格式页 |
| 中文摘要（含关键词） | 课题背景、主要工作、采用技术、实现成果与结论的简短陈述 | 独立完整的短文，便于快速了解全文 |
| 英文摘要（Abstract）与关键词 | 中文摘要的英文翻译 | 学术规范要求 |
| 目录 | 各章节标题及页码（自动生成至三级标题） | 导航，层次清晰 |
| 第一章 绪论 | 研究背景与意义、国内外研究现状、研究内容与目标、论文组织结构 | 为什么做这个课题、做了什么 |
| 第二章 相关技术与理论基础 | 关键技术介绍、核心理论原理阐述、开发环境与工具 | 用什么技术做、理论依据是什么 |
| 第三章 系统分析 | 需求分析（功能/非功能）、可行性分析、业务流程分析、用例分析 | 系统要做什么、为什么能做 |
| 第四章 系统设计 | 总体架构设计、功能模块设计、数据库设计（E-R 图＋表结构）、接口设计、关键算法/流程设计 | 系统怎么设计的 |
| 第五章 系统实现 | 开发环境搭建、核心模块代码说明、关键界面展示、运行结果演示 | 怎么实现的、做成了什么样 |
| 第六章 系统测试 | 测试环境、测试方法、测试用例设计、测试结果分析、Bug 修复情况 | 质量如何、是否达到要求 |
| 第七章 总结与展望 | 主要工作与成果、系统不足、未来改进方向 | 收束全文 |
| 参考文献 | 按 GB/T 7714—2015 格式 | 学术规范，不少于 20 篇 |
| 人工智能工具使用声明 | 如实声明 AI 工具使用情况 | 学术诚信要求 |
| 致谢 | 对导师及给予帮助的人员表示感谢 | 真诚简洁 |
| 附录（可选） | 完整源代码清单、配置文件、详细测试数据、调查问卷 | 补充支撑材料 |

**内在逻辑**：绪论提出「为什么要做」→ 技术基础说明「用什么技术和理论」→ 系统分析明确「需要做什么」→ 系统设计规划「怎么构建」→ 系统实现展示「具体怎么做出来的」→ 系统测试验证「做得怎么样」→ 总结收束全文。**全文字数不少于 10000 字**，标题级次、图表编号、格式排版按学院规范标准执行。

## 5 各章节写法

### 题目、摘要与关键词

摘要用**第三人称**陈述，扼要叙述选题背景、研究目的、采用的技术方法、主要实现内容和取得的成果；文字精炼、具有独立性和完整性，**不加评论、补充和解释**，300—500 字。关键词是供检索用的主题词条，应在摘要中出现，一般列 3 至 5 个，按外延层次从大到小排列，**中间用分号隔开**。

摘要写法的骨架可套用：行业/场景背景与现有方式的问题 → 本文设计并实现了什么系统、采用什么架构与设计模式 → 前后端与数据库各用什么 → 实现了哪些核心功能 → 测试结论与价值。

### 第一章 绪论

四部分：① 研究背景与意义（为什么要开发这个系统；意义分理论意义与实践意义）；② 国内外研究现状（同类系统或相关技术的发展历程、成熟产品方案、热点与趋势，指出不足与改进点引出切入点——**要有分析对比，不要写成产品罗列**）；③ 研究内容与目标（完成了哪些工作、实现了哪些模块、达到什么目标，建议分点列出）；④ 论文组织结构。

### 第二章 相关技术与理论基础

体现论文理论深度的关键章节，**避免单纯堆砌技术名词**，要说明「为什么选这项技术」以及「技术原理如何指导设计实践」。三部分：

1. **核心理论基础**：B/S 系统说明 B/S 工作原理、三层架构分层逻辑、MVC/MVVM 设计思想、与 C/S 的对比及选择理由；数据库应用说明关系数据库原理、E-R 模型、规范化理论、事务与并发控制；AI 课题说明所选算法/模型的基本原理、适用场景、优缺点；网络工程说明 TCP/IP 协议栈、子网划分、VLAN、路由协议。
2. **关键技术介绍**：介绍实际使用的主要技术与框架，每个简要说明概念、特点、在本系统中的用途即可，不要照搬官方文档大段介绍。
3. **开发环境与工具**：硬件环境、操作系统、IDE、数据库、服务器、浏览器及版本号。

注意：技术介绍必须与课题紧密相关，不要把不相关的热门技术都写进去。

各类课题的理论基础对应关系见《规范要求》表 7-1（Web 开发 / 移动应用 / 桌面应用 / 游戏 / 数据分析 / 大数据 / 机器学习 / 深度学习 / 网络工程 / 网络安全 / 嵌入式物联网 / 云原生 / 综述 / 教改 各自的核心理论、要点与典型工具）。

### 第三章 系统分析

1. **需求分析**：功能需求——先描述目标用户与使用场景，再**分角色**详细列出每个功能点，建议配用例图（UML Use Case Diagram）；非功能需求——性能（响应时间、并发量）、安全性（密码加密、权限控制）、易用性、兼容性、可扩展性。
2. **可行性分析**：技术、经济、操作、时间四个方面。
3. **业务流程分析**：用流程图描述核心业务（注册登录、商品下单、数据处理流程等）。

### 第四章 系统设计

1. **总体架构设计**：架构图、分层结构（表示层/业务逻辑层/数据访问层）、各层职责与调用关系、部署架构。
2. **功能模块设计**：功能模块图，每个模块的职责、输入输出、处理逻辑。
3. **数据库设计**：概念结构（E-R 图，实体、属性、关系）→ 逻辑结构（E-R 转数据表，列出表名、字段名、类型、主键、外键、约束，建议用表格）→ 设计的优化考虑（索引、范式级别）。
4. **接口设计**（前后端分离项目必须写）：主要 API 的 URL、请求方式、请求参数、返回格式，建议用表格。
5. **关键算法/核心流程设计**：核心功能或复杂算法用流程图或伪代码描述处理逻辑。

### 第五章 系统实现

1. **开发环境搭建**：环境配置过程、工程目录结构。
2. **核心功能模块实现**：按模块逐个介绍——实现思路、核心代码片段（**只贴关键逻辑，完整代码放附录**）、关键界面截图、运行结果说明。截图要清晰、包含完整页面，不要只截局部。
3. **关键代码说明**：核心业务逻辑的代码解释，说明实现了什么功能、采用了什么设计思路。
4. **系统部署说明**（如需要）。

红线：代码和截图必须是**自己实际开发的真实成果**，不得用网络图片或他人项目截图冒充；界面文字、数据要完整合理，不要出现乱码或测试垃圾数据。

### 第六章 系统测试

1. **测试环境**：硬件、软件（操作系统、浏览器、服务器、测试工具）及版本。
2. **测试方法**：单元测试、集成测试、系统测试；功能、性能、兼容性、安全测试。
3. **测试用例设计与执行**：表格列出**测试用例编号、测试功能、前置条件、测试步骤、预期结果、实际结果、是否通过**；须覆盖正常流程与异常流程（非法输入、权限不足等）。
4. **测试结果分析**：统计通过率，说明发现了哪些 Bug、如何修复、修复后效果，给出性能实测数据，客观评价是否达到预期目标。

### 第七章 总结与展望

① 工作总结（完成了哪些工作、实现了哪些功能、解决了什么问题、有什么收获）；② 不足分析（功能、性能、界面、安全、适用场景等，客观）；③ 未来展望（针对不足提出**具体**的改进与扩展方向）。

## 6 参考文献、AI 声明、致谢、附录

**参考文献**按 GB/T 7714—2015，数量不少于 20 篇，期刊论文和学术著作占比不低于 60%，近 5 年文献比例不低于 50%，鼓励引用外文。常见格式：

- 期刊：`[序号] 作者. 题名[J]. 刊名, 年, 卷(期): 起止页码.`
- 专著：`[序号] 作者. 书名[M]. 版本(第 1 版不标注). 出版地: 出版者, 出版年: 起止页码.`
- 学位论文：`[序号] 作者. 题名[D]. 保存地点: 保存单位, 年份.`
- 电子文献：`[序号] 作者. 题名[EB/OL]. (发表日期)[引用日期]. 网址.`

**人工智能工具使用声明**：必须设专节，如实声明 AI 工具名称、版本、使用环节（代码补全、文字润色、bug 排查等）及大致使用比例，本人签字确认；未使用也要明确声明。严禁隐瞒，严禁 AI 全文代写或直接生成核心代码。（**位置见《规范要求》第 2 节的冲突说明，先问指导教师。**）

**致谢**：真诚简洁，避免空泛套话，不超过 500 字。

**附录**：完整核心源代码、配置文件、复杂公式推导、详细测试数据、调查问卷等。

## 8 常见问题警示

**选题阶段**：选题过大过难（想「做一个类似淘宝的电商平台」，14 周做不完只能交半成品）；选题过简（静态页面或简单增删改查，功能模块不足 3 个）；盲目追热点（基础薄弱无法实现核心算法，只能套皮调 API）；选题与专业无关（纯平面设计、纯文案策划）；题目不规范（过长、模糊、口语化）。

**设计阶段**：需求分析缺失，边想边做、频繁变更导致失控；技术选型贪新求异，踩坑无数进度滞后；架构混乱（业务逻辑、数据库操作、界面代码混在一起）；数据库设计随意（无主键外键约束、字段类型不当）；理论基础缺失（第二章只罗列名词，不说明原理与选型理由）。

**开发与写作阶段**：前松后紧（第 10 周后才开始编码）；「截图驱动」开发（用网络教程截图或往届学生截图凑数，系统跑不起来）；代码质量差（无注释、命名随意、大量重复）；论文图文两张皮（只放图表不做分析，或分析与数据不对应）；测试章节敷衍（只用一句「测试通过，系统运行正常」）；对策展望空泛（「未来引入人工智能、大数据让系统更智能」）；结构残缺（缺理论基础章节、缺测试章节、没有 AI 声明、附录缺失）。

**学术规范与诚信**：严禁抄袭剽窃、伪造篡改、买卖论文或代做系统；规范使用 AI 工具并如实披露，隐瞒按学术不端处理；**相似比超过 20% 不得参加答辩，超过 50% 按严重学术不端处理**；源代码全程留痕（Git 记录），答辩教师会针对代码细节、技术原理、设计思路提问。
